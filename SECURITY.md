# TailNow security model

TailNow runs on IPv4 loopback behind Tailscale Serve. Tailscale policy decides which clients can reach each port. Reachable clients may view the directory and apps. Publishing, reordering, minimizing, removing, restoring, and shutting down require an administrator credential. Local administrators and configuration writers are trusted. Do not enable Funnel, public forwarding, or an unauthenticated alternate proxy to private backends.

## Browser and administrator boundaries

Every hosted app has an explicit, unique HTTPS origin in `siteOrigins`. The directory has a separate origin. Different HTTPS ports on the same Tailscale hostname provide separate browser origins for DOM access, local/session storage, IndexedDB, and service workers. Each app origin serves only that app, plus explicitly configured static dependencies. Top-level links may redirect to another app's own origin; they never serve its files under the caller's origin. Application origins cannot serve directory management APIs. Origin assignments and retired shared addresses are recorded in the catalog and cannot be recycled for another app or administration.

**Cookies are scoped to hostnames, not ports.** TailNow does not use cookies for authentication, and its API proxies discard cookies and authorization headers in both directions. Cookie-authenticated external services should use separate hostnames, host-only cookies, and their own CSRF controls. Port isolation alone does not protect a cookie-based service on the same hostname. TailNow does not change the security model of external linked services.

The administrator key contains 256 random bits and is stored in `dataDirectory/admin-token`, owner-only mode 0600. It is never included in HTML, URLs, request logs, or browser persistent storage. The sign-in form exchanges it for a one-hour bearer session held in sessionStorage. The input is cleared immediately. Sessions expire, are bounded to 32, and are revoked on logout or restart. Failed sign-ins are limited. The local publisher reads the private key directly. Rotate it with `scripts/admin-key.js --rotate` and restart the service to invalidate all existing credentials and sessions.

All authenticated requests still require the exact configured Origin, including scheme and port, if a browser sends it. Same-site requests from another port are rejected along with cross-site subresource requests. Browser mutations additionally require a custom header; this is CSRF protection, not authentication. No CORS permission is granted. Client-supplied proxy identity headers and Host alone never grant administrator privileges. Admin responses use a restrictive CSP, `no-store`, frame denial, opener isolation, and origin-keyed agent clusters.

## Upgrading a shared-origin installation

Follow [the migration guide](docs/security-migration.md). Administration must move to a fresh origin, and hosted content must stop being served from the old shared origin. Old shared paths become redirects or narrowly scoped browser-storage migration pages. Do not leave a second Tailscale route exposing a backend outside its new app origin.

Optional `storageKeys` belong to exactly one app. Visiting its old HTTPS root copies only those named localStorage values into empty slots on the new origin. It never overwrites existing values, and removes an old value only after acknowledged copying and only if the source has not changed. The receiver authenticates the parent origin, frame, app, and message nonce. Automatic migration requires the same HTTPS hostname; cross-host iframe storage can be partitioned, so that case retains the source and requires manual export/import. Temporary sessionStorage and cookies are not migrated. Migration cannot undo disclosure that happened before isolation or remove malicious scripts already cached in an old browser tab. Close old app tabs after migration.

Explicit `dependencies` grant the consuming app access to another site's files, including executable content. Grant only deliberate, trusted asset bundles. A fixed `apiProxies` entry grants one app access to a configured loopback backend and method allowlist. It accepts no caller-controlled destination, rejects redirects, bounds request/response sizes and time, and does not forward credentials, identity headers, cookies, or CORS headers. The backend remains responsible for its own data validation and concurrency rules.

## Files, publishing, and availability

Storage paths are resolved through the filesystem before comparison, including parent symlinks and case aliases. Private storage, served legacy files, and configuration cannot overlap. The HTTP dispatcher denies dotfiles, traversal, symlinks, private catalog files, old releases, and application source outside the selected release. Errors omit filesystem paths, command output, and parser diagnostics.

All mutations share one process lock. ZIP uploads are authenticated before receiving multipart data, written outside served paths, and extracted in a worker with a deadline and memory bound. Limits cover compressed bytes, entry count, per-file expansion, total expansion, CRC integrity, duplicate names, symlinks, special files, and path traversal. A failed upload cannot replace or remove the active app. One atomic catalog update selects a validated release and updates visibility. State writes use private files and flush before rename.

Publishing reserves worst-case upload/extraction space before receiving data. Defaults limit private storage to 5 GiB, require 512 MiB of remaining free disk, and retain three releases per app including the active one. Old inactive releases are pruned before publishing and after successful activation. Stopped apps retain their most recent releases for recovery. Failed-worker remnants after a hard process kill count against the quota; an administrator may need to remove them. Backups and legacy sites are outside this quota. Back up private storage and run only one process per catalog.

Standalone shutdown invokes `/bin/launchctl` without a shell, using validated local labels in the service account's GUI domain. TailNow's own service label is rejected. Disable, bootout, and verification prevent KeepAlive from silently restarting the app. Shared infrastructure must never be assigned as an app shutdown target. Hosted shutdown unpublishes the app and retains its files.

Node must be a patched 24.x release, at least 24.22.3. Install locked dependencies with `npm ci --ignore-scripts` and check `npm audit`. Automated tests cover authentication, browser isolation, migration, malicious uploads, storage aliases, quotas, lifecycle persistence, and API compatibility. These tests are evidence for the implemented boundaries, not a guarantee that every vulnerability has been found. Reachable clients can still consume bounded server resources; TailNow is not a public multi-tenant hosting service. Hosted app code, external services, operating-system security, Tailscale policy, and physical access need their own review.
